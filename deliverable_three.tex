\subsection{FR11. Identity and access management} \label{FR11}
The system shall provide identity and access management through the following functionalities:
\begin{itemize}
    \item \textbf{FR11.1 \hl{Patient} registration:} The system shall allow unregistered patients to create a new account using their email by providing the personal data required for identification, verification and service usage.

    \item \textbf{FR11.2 \hl{Patient} validation:} The system shall allow newly registered patients to validate their accounts by verifying a secure token sent to their registered email address.

    \item \textbf{FR11.3 User login:} The system shall allow registered users in the standard User hierarchy to authenticate and securely access their accounts using their registered email and password credentials, or alternatively through national digital identity providers (e.g., SPID, CIE).

    \item \textbf{FR11.4 \hl{System Administrator authentication}:} The system shall allow an active account with administrative privileges to authenticate through the dedicated administration interface using its email address and password. 
\end{itemize}
\vspace{0.3cm}

The term "User" has been replaced with "Patient" in FR11.1 and FR11.2 because registration and validation apply specifically to patients. FR11.3 remains applicable to the standard User hierarchy defined in D2. FR11.4 is a new functional requirement introduced during implementation to document the separate System Administrator authentication flow, which was implemented but not covered by FR11.3.

\section{Context Description}

\subsection{General Overview}
This project involves the design of an extensive and centralized software application, intended for use in the administration of the operations of a network of private healthcare services spread over the Italian territory. This application, operating exclusively on an outpatient and ambulatory model, seeks to digitalize key administrative operations, thereby optimizing the entire experience for all relevant stakeholders involved in the healthcare sector.

At the heart of this application is the ``Examination,'' defined as a specific, scheduled transaction between a patient and a doctor. In order to support this model, the application will offer medical professionals tools for scheduling, administrators an extensive toolset for overseeing hospital operations, and patients an optimized interface for scheduling examinations and processing transactions.

The specific features and step-by-step operations for each of these stakeholders will be discussed in the objectives and requirements sections of the application.

\subsection{System Boundaries}
A major technical limit of this system is its ability to integrate with third-party insurance providers. The application will be unable to verify policies in real time, as it will not have access to any external, live databases from third-party insurance providers. The system will, therefore, rely on a simulated system for managing patient insurance information, with codes created internally. The process of reconciling insurance claims and outstanding debts owed to the hospital will, therefore, not be automated but will be internally simulated.

In addition, the fact that the platform has been specifically designed for the logistics of the scheduled outpatient examinations means that the current scope of the system has been specifically defined in terms of doctors, facility managers, and patients. There has been no specific design of the system in terms of dedicated interfaces and access levels for other professional figures in the hospital scenario, such as nurses, medical technicians, and administrative secretaries.
      
Furthermore, the administration of medications and pharmaceuticals is completely out of the scope of this project. The functionality of the application still remains completely focused on the administration and processing of medical consultations.

\subsection{Architecture Type: 3-Tier Architecture}
\phantomsection 
\subsubsection{Description}

The application follows a \textbf{3-Tier Architecture} pattern, separating the system into three distinct layers:

\begin{itemize}
  \item \textbf{Presentation Layer (Frontend)} --- React with Vite
  \item \textbf{Business Logic / API Layer (Backend)} --- Django REST Framework
  \item \textbf{Data Layer (Database)} --- PostgreSQL
\end{itemize}
\phantomsection 
\subsubsection{Why 3-Tier?}

\begin{itemize}
  \item \textbf{Maintainability:} Each tier can be developed, tested, and maintained independently. Changes in one layer do not directly affect others.
  \item \textbf{Separation of Duties:} Clear separation between UI concerns, business logic, and data persistence. Frontend developers focus on UX, backend developers focus on APIs and business rules, and database administrators manage data integrity.
  \item \textbf{Scalability:} Each tier can be scaled independently based on demand. The frontend can be served via CDN, the API can be load-balanced, and the database can use replication.
  \item \textbf{Industry Standard:} 3-tier is the most widely adopted pattern in modern web development, making the codebase more familiar to new team members.
\end{itemize}

\textbf{Why React?}

\begin{itemize}
  \item \textbf{Reusable Components:} React's component-based architecture allows building modular, reusable UI pieces that reduce code duplication.
  \item \textbf{Flexibility for Routing:} React Router DOM enables client-side routing, allowing seamless navigation without full page reloads.
  \item \textbf{Security Measures:} React provides built-in protections against common vulnerabilities like XSS attacks through automatic escaping.
  \item \textbf{Large Ecosystem:} Extensive community support, libraries, and tools available.
  \item \textbf{Developer Experience:} JSX syntax makes code more readable and maintainable.
\end{itemize}

\textbf{Why NOT Plain HTML/CSS?}

\begin{itemize}
  \item Plain HTML/CSS is considered outdated for modern web applications and not an industry standard.
  \item Lacks dynamic interactivity without extensive custom JavaScript.
  \item No component reusability or state management capabilities.
  \item Poor performance with complex UIs.
\end{itemize}

\begin{itemize}
  \item Included as the framework of choice for this project.

  \item Strong security features (CSRF protection, SQL injection prevention, etc.).
  \item Well-documented and widely used in production environments.

    \item \textbf{Patient:} This actor represents a patient within the healtcare system, whose main functionalities regard the booking and management of appointments.
    \item \textbf{Doctor:} This actor represents a general doctor within a healtcare system, including Head of Hospital and Head of Department. A Doctor's main functionalities regard the management and tracking of examinations and the consultations of Patients' medical records.
    \item \textbf{Head of Hospital:} This actor represents a specific doctor who was appointed as the head of a hospital, whose main fuctionalities regard the management of an hospital facility
    \item \textbf{Head of Department:} This actor represents a specific doctor who was appointed as the head of a department, whose main functionalieties regard the management of a department within an hospital facility.
\end{itemize}

\subsection{Infrastructure}
The project's infrastructure is managed using a \texttt{docker-compose.yml} file. This configuration orchestrates the core services that make up the solution:
\begin{itemize}
    \item Development environment
    \item Nginx reverse proxy
    \item PostgreSQL database
    \item Mail service
\end{itemize}

\begin{center}
    \includegraphics[width=0.8\textwidth]{ScreenshotD3/code_snippets/infra.png}
    \captionof{figure}{Snippet of the \texttt{docker-compose.yml} configuration}
\end{center}

Each service defined within the Docker Compose file typically consists of the following key components:
\begin{itemize}
    \item \textbf{Image / Build context}: A pre-existing Docker image or a custom \texttt{Dockerfile} used to build the container.
    \item \textbf{Environment variables}: Configuration values injected into the service, often loaded dynamically from a \texttt{.env} file.
    \item \textbf{Volumes}: Persistent storage mechanisms that map container directories to the host file system, ensuring data is not lost when containers are destroyed or recreated.
    \item \textbf{Port mapping}: Network rules that expose the container's internal ports to the host machine, allowing external access to the service.
\end{itemize}

\subsection{Models}
The core entities mapped to the database are structured using Django models. 

\begin{center}
    \includegraphics[width=0.8\textwidth]{ScreenshotD3/code_snippets/model.png}
    \captionof{figure}{Snippet of the \texttt{medical/models.py} file}

These model classes can extend custom utility mixins (such as \texttt{CreatedUpdatedAt} and \texttt{SoftDelete}), which inherently derive from Django's base \texttt{models.Model}. 

Within each model definition, the following key elements are established:
\begin{itemize}
    \item \textbf{Fields and Data Types}: The parameters that define the internal structure of the entity.
    \item \textbf{Relationships}: The relational mappings between different tables (e.g., Foreign Keys).
    \item \textbf{Custom Methods}: Encapsulation of specific business logic directly within the model class.
    \item \textbf{Method Overrides}: Customization of default built-in behaviors, such as overriding the \texttt{\_\_str\_\_} method for better object representation.
\end{itemize}
\phantomsection
\subsection{Serializers}
Serializers act as a crucial intermediary layer between the database models and the client applications. They serve two primary purposes:
\begin{itemize}
    \item \textbf{Data Validation}: Ensuring that incoming data meets all required constraints before interacting with the database.
    \item \textbf{Data Transformation and Formatting}: Converting complex data types (like Django models and querysets) into native Python datatypes that can be easily rendered into JSON, and vice versa.
\end{itemize}

\begin{center}
    \includegraphics[width=0.8\textwidth]{ScreenshotD3/code_snippets/serializer.png}
    \captionof{figure}{Snippet of the \texttt{users/serializers.py} file}
\end{center}

In the provided example, the serializer is explicitly customized to handle user creation logic. Key operations defined within this class include:
\begin{itemize}
    \item \textbf{Field Definition}: Specifying the exact parameters to be accepted and processed by the API.
    \item \textbf{Field Overrides}: Modifying default field behaviors, such as explicitly setting the password field to \texttt{write\_only} to ensure it is never exposed in API responses.
    \item \textbf{Custom Validation}: Implementing specific field-level validation logic (e.g., \texttt{validate\_fiscal\_code}) to enforce strict data integrity rules.
    \item \textbf{Method Overriding}: Customizing the default \texttt{create} method to safely process sensitive information, such as extracting (\textit{popping}) the password from the validated data.
\end{itemize}

\phantomsection
\subsection{Views}
Views serve as the entry points for the application's API endpoints. They act as the core controllers within the architecture, responsible for receiving incoming HTTP requests, orchestrating the necessary business logic, and returning the appropriate HTTP responses to the client.

\begin{center}
    \includegraphics[width=0.8\textwidth]{ScreenshotD3/code_snippets/view.png}
    \captionof{figure}{Snippet of the \texttt{users/views.py} file}
\end{center}

In the provided example, the view is specifically designed to handle the user login process via a \texttt{POST} request. The typical execution flow within this view involves several key steps:
\begin{itemize}
    \item \textbf{Data Ingestion}: Capturing the payload (credentials) sent by the client in the request body.
    \item \textbf{Validation}: Passing the incoming data to the \texttt{LoginSerializer} to ensure it is structurally valid and meets all required constraints before any processing occurs.
    \item \textbf{Authentication Logic}: Attempting to authenticate the user by verifying the validated credentials against the database records.
    \item \textbf{Response Generation}: Returning a structured HTTP response based on the authentication outcome. This typically means returning an authentication token (e.g., JWT) with a \texttt{200 OK} status on success, or returning explicit error messages with a \texttt{400 Bad Request} or \texttt{401 Unauthorized} status if the login attempt fails.
\end{itemize}

\subsection{URL Routing}
URL routing serves as the final configuration layer, actively exposing the application's API endpoints to external users, client applications, and interconnected services. 

\begin{center}
    \includegraphics[width=0.8\textwidth]{ScreenshotD3/code_snippets/urls.png}

Django's URL dispatcher provides a highly flexible approach to endpoint management, characterized by two main features:
\begin{itemize}
    \item \textbf{Nested Architecture}: URL configurations can be modularly included and deeply nested. This allows developers to cleanly separate global routing rules from app-specific endpoints, ensuring the codebase remains scalable and maintainable.
    \item \textbf{RESTful Conventions}: The routing system seamlessly accommodates standard RESTful API design, providing out-of-the-box support for intuitive naming patterns, path parameters, and resource-oriented structuring.
\end{itemize}

The Front-End API handler serves as the centralized HTTP client for the application. Built on top of the \texttt{axios} library, this module establishes a consistent and highly reusable foundation for all outgoing network interactions between the client and the backend services.

By analyzing the provided implementation, several key architectural patterns are defined within this module:
\begin{itemize}
    \item \textbf{Axios Configuration}: Initialization of a dedicated Axios instance pre-configured with common attributes, such as the \texttt{baseURL}. This eliminates the need to hardcode the API domain across different UI components.
    \item \textbf{Standardized Response Wrapper}: The implementation of a unified \texttt{request} utility function that resolves API promises. It ensures every call consistently returns an object structured as \texttt{\{ok: boolean, data: object\}}, which simplifies loading and error state management in the UI layers.
    \item \textbf{Centralized Error Handling}: The wrapper gracefully catches exceptions, explicitly differentiating between valid backend error responses (e.g., HTTP 400/500 errors) and network failures (e.g., server unreachable), providing safe fallback messages.
    \item \textbf{Modular API Methods}: Specific endpoint interactions, such as the \texttt{register} method, are encapsulated within an exported \texttt{websiteApi} object. This keeps React components decoupled from routing paths and HTTP verbs, improving code maintainability.
\end{itemize}
